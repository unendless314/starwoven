# 星靈織語 Starwoven — 星靈扭蛋規格書 v0.1（草案）

> **文件狀態**：v0.1 **草案，待開發者確認細節**（2026-11-05）。尚未登錄 `decisions.md`；開發者確認方向後新增 DEC-083，再進入設計審查與實作。
> **建立日期**：2026-11-05
> **沿革摘要**：v0.1 依 2026-11-04 業主會議提出之「付費客人抽獎體驗其他服務」構想，經開發者與 AI 規格討論後整理而成。
> **定位**：**MVP**——規則從簡、易於迭代，不追求最終形態；只處理方向性問題，細節（名額、過期、折抵核銷等）先由人工於試算表與 LINE 處理，待實際使用數據出現後再決定是否程式化。
> **核心目標**：**交叉銷售**——讓只購買單一服務的客人，透過抽籤獲得「另一項服務」之短時體驗，進而購買該服務之完整諮詢或對應之固定課程。成效指標為**體驗後之付費轉換**，而非發出之體驗數量。
> **技術路線**：比照課程許願池（`course_wishlist_plan_v3.md`）——Google Apps Script＋試算表為 SSOT，前端以 JSONP 呼叫；**不使用 VPS Node 服務、不新增資料庫**。官方發碼以 **Google 表單**為操作介面（第五節第 4 小節），試算表對小編僅開放檢視。
> **帳號歸屬**：MVP 之試算表、表單、Apps Script 皆建立於**開發者帳號**下；確認使用效果良好後，再評估移轉至官方帳號（屆時須於新帳號重建觸發器）。

## 一、 設計原則

1. **抽的是「哪一項」，不是「有沒有」**：持私訊碼之付費客人必定獲得一項體驗，抽籤只決定項目——付費客人不會落空。
2. **伺服器決定結果**：抽籤由 Apps Script 執行並寫入試算表；前端只負責儀式動畫，不決定結果、無法重抽（同 `ai_platform_plan.md` 第一節第 3 條之精神）。
3. **骨架穩定、規則外置**：資料模型固定為「抽獎碼 → 抽獎紀錄」；獎池、名額、碼的啟用與否皆由業主於試算表調整，不需改程式或重新部署。
4. **依實體分表，不依來源分表**：私訊碼與公開碼為同一實體（抽獎碼）之不同「類型」，以欄位區分；新增發碼來源＝新增一種欄位值，不新增工作表。
5. **一個功能一個試算表檔案**：星靈扭蛋使用獨立試算表與獨立 Apps Script，與許願池互不影響（故障、權限、部署各自隔離）。
6. **機率不加權**：獎池中「開放」之項目均等機率。
7. **不捏造內容**：結果頁、說明頁與活動貼文文案由業主定稿；規格書與程式中之文案皆為佔位。

## 二、 範疇

### 1. MVP 包含

| 項目 | 說明 |
| :--- | :--- |
| 頁面 | `/gacha` 單頁（靜態），**`noindex`、不加入導覽列**（比照 `/tarot`）；深淺雙模式、行動裝置優先 |
| 入口 | LINE 私訊之抽獎連結、社群貼文之公開碼；有公開活動時可另以首頁輪播海報導入（DEC-068 既有機制） |
| 抽獎碼 | 兩種類型：**一次性**（私訊碼）、**公開**（社群共用碼，可設使用上限） |
| 抽籤 | Apps Script 於「開放」之獎池項目中均等抽一項；排除該碼登錄之「已購項目」 |
| 結果頁 | 顯示抽中項目與**抽獎編號**，引導至官方 LINE 登記／預約 |
| 紀錄 | 每次抽籤寫入「抽獎紀錄」工作表，供人工核對與統計 |
| 後台（發碼） | Google 表單 A（發放付費碼）、B（建立公開碼）；程式產生抽獎碼並將抽獎連結寄至填寫者 Gmail；填寫者須在授權名單內 |
| 追蹤 | GA4 事件（前綴 `gacha_`；不含抽獎碼） |

### 2. MVP 明確不做

- 不加入導覽列、不開放搜尋引擎索引。
- **不做無碼抽獎**（任何人點進來即可抽）：無身分可識別、Apps Script 無法取得訪客 IP，無法防重抽；若日後需要，另立 DEC 作為獨立產品評估。
- 不做每日限量／隨機開放時段（流量不足時反效果，見第九節）。
- 不做機率加權、每月名額自動計算、過期自動判斷、加價購自動折抵——皆先人工處理。
- 不做會員、線上金流、與 LINE 帳號綁定。
- 不使用 VPS Node 服務與 AI。

## 三、 商業規則（暫定，待業主確認）

### 1. 體驗內容

| 項目 | 暫定值 | 備註 |
| :--- | :--- | :--- |
| 體驗時長 | **15 分鐘** | 正規諮詢多為 30／60 分鐘；更短不恰當、更長有成本與排擠付費客群之疑慮 |
| 體驗範圍 | 針對一個問題之初探 | 須明確定義，避免客人要求在 15 分鐘內完成完整諮詢；結尾以固定話術導向完整服務 |
| 有效期限 | 待定（建議 30～45 天） | MVP 由人工判斷 |
| 老師報酬 | **暫無** | 日後由業主設立預算作為激勵與成本控制 |

### 2. 獎池

依 `content_inventory.md` 第 2.2 節之服務項目，**八字命理除外**：

| 獎池項目 | 對應之固定課程（加價購承接） |
| :--- | :--- |
| 塔羅占卜 | 偉特塔羅團練／托特塔羅循環班 |
| 星盤解析 | 占星循環班 |
| 生命靈數 | 生命靈數循環班 |
| 靈氣與光調頻 | 七脈輪與靈氣 |
| 阿卡西紀錄 | 光與阿卡西紀錄 |
| 毛孩溝通 | （無對應課程，僅可導向完整服務） |

- 抽籤時排除該抽獎碼之「已購項目」（例：買塔羅者不會抽到塔羅）。
- 業主可於「獎池設定」工作表將當月量能不足之項目改為「暫停」，其餘項目仍均等抽。

### 3. 升級路徑（加價購）

- **僅限抽中之項目**：抽中占星體驗者，可以優惠報名占星循環班；不提供「喜歡塔羅就直接拿塔羅課程優惠」之路徑——優惠只用在把客人帶進新領域。
- 形式建議為**課程首月固定金額折抵**（金額與期限待定，建議 200～300 元、體驗後 14～30 天內），不採加送時數（老師無報酬，不宜再增加負擔）。
- 無對應課程之項目（毛孩溝通）改為完整服務之折抵。
- MVP 由人工於 LINE 處理，結果頁只顯示固定說明文案。

### 4. 兩種抽獎碼

| | 一次性碼（私訊） | 公開碼（FB／Threads／IG） |
| :--- | :--- | :--- |
| 取得方式 | 付費客人於 LINE 完成付款後，由小編私訊連結 | 業主於社群貼文公布 |
| 一碼一人 | 是 | 否，多人共用 |
| 使用上限 | 1 次（重複兌換回傳原結果） | 可設定（例：前 20 名），達上限後失效；留白＝不限 |
| 承諾 | **保證提供體驗** | **不保證**，依當月老師排班與量能安排 |
| 主要用途 | 兌現贈品、交叉銷售 | 流量來源統計、吸引加入官方 LINE 好友 |
| 去重 | 碼本身唯一 | 於 LINE 端人工處理：每個 LINE 帳號每個活動限登記一次 |

- 公開碼之文案須避免「抽中贈送」等保證性用語，明示名額有限、依登記順序安排；建議準備保底選項（例：名額用完者改提供小額折抵）。文案由業主定稿。
- 公開碼搭配使用上限，即可於社群製造「不定時發碼、限量先搶」之稀缺感，且名額＝該波活動之量能上限。

## 四、 系統架構

```
訪客瀏覽器
  └─ GET  /gacha?code=XXXX            → nginx 直接回傳靜態 HTML（noindex）
  └─ JSONP GET <Apps Script URL>       → Google Apps Script（星靈扭蛋專用）
                                           1. 讀取抽獎碼表：碼存在、狀態為啟用
                                           2. LockService 取得鎖
                                           3. 一次性碼：已有紀錄 → 回傳原結果
                                              公開碼：已達使用上限 → 回傳額滿
                                           4. 讀取獎池設定（開放項目，排除已購項目）
                                           5. 均等抽一項 → 寫入抽獎紀錄（產生抽獎編號）
                                           6. 釋放鎖 → 回傳結果
```

官方發碼（後台）：

```
小編／業主手機
  └─ Google 表單 A／B 送出（收集已驗證之電子郵件）
       → 表單自動寫入各自之「表單回應」工作表
       → onFormSubmit 觸發器（同一 Apps Script 專案）
            1. 比對填寫者 email 是否在「授權名單」
            2. LockService 取得鎖 → 產生抽獎碼 → 寫入「抽獎碼」工作表 → 釋放鎖
            3. 寄送抽獎連結（或失敗原因）至填寫者 Gmail
```

- 客人兌換（`doGet`）與官方發碼（`onFormSubmit`）為**同一個綁定於試算表之 Apps Script 專案**；兩者皆會寫入試算表，一律於 `LockService` 鎖內寫入。
- 傳輸採 JSONP（DEC-067：行動裝置 fetch 被 Apps Script 302 跨網域轉址阻擋）。抽獎碼因此會出現在請求網址中；碼為一次性或本即公開，風險可接受。
- 前端環境變數：`PUBLIC_GACHA_API_URL`（Apps Script web app URL，比照 `PUBLIC_WISHLIST_API_URL`）。未設定時之行為待定（見第十節）。
- **共用表面影響（實作時）**：`.env.example`（新增變數）、`AGENTS.md`（路由表、環境變數）；不修改 `Navbar.astro`、`Layout.astro`（`noindex` prop 已存在）、nginx、VPS 服務。

### 5. 後台：Google 表單發碼

非程式背景之兼職團隊不宜手打隨機碼或直接編輯試算表；發碼一律經 Google 表單，由程式產生抽獎碼。

| 表單 | 欄位（皆以表單內建驗證防呆） | 使用者 |
| :--- | :--- | :--- |
| **A. 發放付費碼** | 已購項目（下拉，含「不指定」） | 小編 |
| **B. 建立公開碼** | 活動代號（規則運算式驗證）、使用上限（數字，留白＝不限）、自訂碼（選填，規則運算式驗證） | 業主／社群負責人 |
| （可選）C. 更新處理狀態 | 抽獎編號（規則運算式驗證）、狀態（下拉） | 小編；MVP 可先由管理者直接於試算表更新 |

- **身分驗證**：表單開啟「收集已驗證之電子郵件」（填寫者須登入 Google）；程式比對「授權名單」，不在名單內則不發碼。表單連結外流亦無法發碼。
- **取得連結**：表單送出後無法於畫面即時顯示產生之碼 → 程式將抽獎連結寄至填寫者 Gmail（主旨含類型、已購項目、時間，例：「【星靈扭蛋】付費碼（塔羅）11/05 14:32」）；發碼失敗（例：自訂碼重複、未授權）亦寄信說明原因。一般 Gmail 帳號每日寄信額度約 100 封，足夠 MVP 使用。
- **一次性碼**自動帶入：類型 `一次性`、活動代號 `purchase`、使用上限 1、狀態 `啟用`；抽獎碼以 8 碼隨機英數產生（排除 0／O、1／I／L），程式確認不與既有碼重複。
- **公開碼**：自訂碼留白則由程式隨機產生；自訂碼與既有碼重複時不建立並寄信通知。

### 6. 權限與分工

| 角色 | 工具 | 試算表權限 |
| :--- | :--- | :--- |
| 小編 | 表單 A（及 C）、Gmail、LINE | 僅檢視 |
| 業主／管理者 | 表單 B；直接編輯獎池設定、授權名單、抽獎碼之狀態與備註 | 可編輯 |
| 客人 | 官網 `/gacha` | 無 |

### 7. 避免表單與程式互相干擾

1. 表單只寫入各自之「表單回應」工作表；程式**只讀取、不修改**回應工作表，正式資料寫入抽獎碼工作表——兩者寫入範圍不重疊，表單題目結構亦不與資料模型綁定。
2. 程式依**欄位標題**讀取回應，不依欄位位置（表單題目增修後欄位順序可能改變）。
3. 回應工作表不得手動插欄、刪列或排序（寫入說明分頁）。
4. `onFormSubmit` 為可安裝觸發器，以建立者帳號身分執行；帳號移轉時須重建。

## 六、 Apps Script 介面（概念）

單一動作 `redeem(code)`，回應形狀待實作時定稿：

| 情境 | 回應 |
| :--- | :--- |
| 抽籤成功（含一次性碼重複兌換） | 抽中項目、抽獎編號、是否為重複兌換 |
| 碼不存在 | 錯誤：無效抽獎碼 |
| 碼已停用 | 錯誤：活動已結束 |
| 公開碼達使用上限 | 錯誤：本次名額已滿 |
| 獎池無可抽項目 | 錯誤：暫無可抽項目 |
| 取鎖逾時／其他 | 錯誤：請稍後再試 |

- **必做**：碼須隨機不可猜；一次性碼重複送出回傳**同一結果**（冪等，非錯誤）；兌換全程於 `LockService` 鎖內完成，避免連點造成重複抽籤（許願池 DEC-035／039 之併發教訓）。
- 隨機數使用 Apps Script 伺服器端產生；不接受前端傳入任何影響結果之參數（如指定項目）。
- 客人兌換端點（`doGet`，匿名公開）**不得提供任何發碼或修改功能**；發碼只經表單觸發器（第五節第 5 小節）。

## 七、 前端（`/gacha`）

- 網址帶 `?code=` 時自動填入，訪客只需按下扭蛋按鈕；保留手動輸入框作為備用。
- 抽籤儀式動畫（形式待定；可參考抽卡頁之儀式感），`prefers-reduced-motion` 時略過。
- 結果頁：抽中項目、抽獎編號、「截圖並傳送至官方 LINE 登記」之指引與 LINE 連結（固定 URL，見 `AGENTS.md`）；公開碼另顯示「名額有限、依登記順序安排」說明。
- 公開碼：同一瀏覽器再次進入時直接顯示上次結果（localStorage，try/catch 包覆；只減少無心重複，不作為防濫用機制）。
- 無碼進入：顯示扭蛋說明與「如何取得抽獎碼」（文案待業主定稿）。
- 深淺雙模式、鍵盤操作、`aria-live`；GA 事件前綴 `gacha_`，不送出抽獎碼。

## 八、 營運流程

### 1. 付費客人（一次性碼）

1. 客人於 LINE 完成付款。
2. 小編以手機填寫表單 A（選擇已購項目）送出，於 Gmail 收到抽獎連結後複製私訊客人。
3. 客人點連結抽籤，截圖結果傳回 LINE。
4. 小編依抽獎編號核對紀錄，安排 15 分鐘體驗並更新處理狀態；體驗後依升級路徑引導報名。

### 2. 社群活動（公開碼）

1. 業主填寫表單 B（活動代號、使用上限、選填自訂碼）建立公開碼，於 Gmail 收到後於社群貼文公布。
2. 訪客抽籤後加入官方 LINE、傳送抽獎編號登記。
3. 小編每個 LINE 帳號每個活動只受理一次登記，依當月量能安排體驗或提供保底選項。
4. 活動結束將狀態改為 `停用`。

### 3. 量能調整

- 某項目當月忙不過來 → 「獎池設定」改為 `暫停`。
- 公開活動名額 → 以抽獎碼之「使用上限」控制。

## 九、 已評估、暫不採用之方案

| 方案 | 不採用理由 |
| :--- | :--- |
| 抽中與否之抽獎（可能落空） | 付費客人落空會降低滿意度，與目標相反 → 改為必中、抽項目 |
| 演算法簽章碼（不需登錄即可驗證真偽） | 適用於大量發碼；本案發碼量小且每碼須記錄來源與已購項目 → 採**白名單制**：只有已登錄於「抽獎碼」工作表且狀態為啟用之碼有效 |
| 人工於試算表手打抽獎碼 | 非程式背景之團隊易打錯、重複或打成規律字串 → 由程式產生 |
| 試算表自訂選單（按鈕發碼） | Google 試算表手機 App 不支援自訂選單與對話框，小編多以手機作業 |
| 試算表 `onEdit`（填一列、程式補齊） | 可行，但小編須有試算表編輯權，防呆僅靠下拉選單與保護範圍 → 改用表單 |
| 自製 Apps Script 後台 Web App | 開發量較大；以擁有者身分執行時，一般 Gmail 帳號通常無法取得使用者 email，須另設管理密碼 → 表單之已驗證 email 較簡單 |
| 私訊碼、公開碼各一張工作表 | 欄位與邏輯重複，新增來源須再開表 → 改以「類型」欄位區分 |
| 加入導覽列 | 無碼訪客進入即為死路；導覽列已滿（DEC-082 之 1024px 考量） |
| 官網每日限量（隨機時段開放、每日上限 20 次）、無碼可抽 | 流量不足時計數器長期不動，反而暴露低流量；隨機時段需要既有主動回訪受眾；無身分無法防重抽；贈品為老師無償時間，對匿名大眾開放無成本上限 → 改以「公開碼＋使用上限」於社群製造稀缺感 |
| 以 VPS Node 服務＋資料庫實作 | 違反 AI 功能「不保存使用者內容」之架構原則、增加維運；試算表讓兼職團隊可直接管理 |

- 備註：官網回訪價值之根本在於內容。「每日內容」（例：延伸占星抽卡之「今日星靈訊息」）為另一題目，不併入本 MVP。

## 十、 待決事項

### 1. 待業主決定

1. 資格門檻：哪些消費可獲得一次性碼（建議以單次消費金額為準，例：600 元以上；塔羅收費結構與其他服務不同，無 60 分鐘方案）；離線文字占卜（一題 300 元）是否計入。
2. 體驗有效期限。
3. 加價購折抵金額與期限。
4. 公開碼之保底選項與「不保證提供服務」之對外用語。
5. 頁面、結果頁、社群貼文文案。
6. 「抽獎紀錄」處理狀態之分類。
7. 老師激勵預算（日後）。

### 2. 待開發者決定

1. `PUBLIC_GACHA_API_URL` 未設定時之行為：顯示「暫未開放」，或比照許願池提供本機 Demo 模式（Demo 模式須明確標示，避免被誤認為正式結果）。
2. 抽籤儀式動畫形式。
3. Apps Script 回應格式與錯誤代碼。
4. 抽獎編號格式。
5. 是否製作表單 C（更新處理狀態）。

### 3. 實作時須實測

1. 表單「收集已驗證之電子郵件」於一般 Gmail 帳號下之行為，以及 `onFormSubmit` 能否穩定取得填寫者 email。
2. 多張表單連結同一試算表時，觸發器依回應工作表區分來源表單之做法。
3. 寄信抵達時間（手機 Gmail 通知）是否足以支應 LINE 即時回覆客人。

### 4. 法規備註

- 公平會《事業提供贈品贈獎額度辦法》對附贈贈品有價值上限（印象中消費 100 元以上者，贈品價值不得超過消費金額之二分之一）；正式推出前請確認現行規定。
