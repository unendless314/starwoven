> **定位**：**MVP**——規則從簡、易於迭代，不追求最終形態；只處理方向性問題，細節（名額、過期、折抵核銷等）先由人工於試算表與 LINE 處理，待實際使用數據出現後再決定是否程式化。
> **核心目標**：**交叉銷售**——讓只購買單一服務的客人，透過抽籤獲得「另一項服務」之短時體驗，進而購買該服務之完整諮詢或對應之固定課程。成效指標為**體驗後之付費轉換**，而非發出之體驗數量。
> **技術路線**：比照課程許願池（`course_wishlist_plan_v3.md`）——Google Apps Script＋試算表為**抽籤結果**之 SSOT，前端以 JSONP 呼叫；**不使用 VPS Node 服務、不新增資料庫**。官方發碼以 **Google 表單**為操作介面（第五節第 5 小節），試算表對小編僅開放檢視。公開活動之**名額**不由試算表判定，而以 LINE 人工登記為準（第三節第 4 小節）。
> **帳號歸屬**：MVP 之試算表、表單、Apps Script 皆建立於**開發者帳號**下；確認使用效果良好後，再評估移轉至官方帳號（屆時須於新帳號重建觸發器）。

## 一、 設計原則

1. **抽的是「哪一項」，不是「有沒有」**：持私訊碼之付費客人必定獲得一項體驗，抽籤只決定項目——付費客人不會落空。
2. **伺服器決定結果**：抽籤由 Apps Script 執行並寫入試算表；前端只負責儀式動畫，不決定結果、無法重抽（同 `ai_platform_plan.md` 第一節第 3 條之精神）。
3. **骨架穩定、規則外置**：資料模型固定為「抽獎碼 → 抽獎紀錄」；獎池、名額、碼的啟用與否皆由業主於試算表調整，不需改程式或重新部署。
4. **依實體分表，不依來源分表**：私訊碼與公開碼為同一實體（抽獎碼）之不同「類型」，以欄位區分；新增發碼來源＝新增一種欄位值，不新增工作表。
5. **一個功能一個試算表檔案**：星靈扭蛋使用獨立試算表與獨立 Apps Script，與許願池互不影響（故障、權限、部署各自隔離）。
6. **機率不加權**：獎池中「開放」之項目均等機率。
7. **不捏造內容**：結果頁、說明頁與活動貼文文案由業主定稿；規格書與程式中之文案皆為佔位。

## 二、 範疇

### 1. MVP 包含

| 項目 | 說明 |
| :--- | :--- |
| 頁面 | `/gacha` 單頁（靜態），**`noindex`、不加入導覽列**（比照 `/tarot`）；深淺雙模式、行動裝置優先 |
| 入口 | LINE 私訊之抽獎連結、社群貼文之公開碼；有公開活動時可另以首頁輪播海報導入（DEC-068 既有機制） |
| 抽獎碼 | 兩種類型：**一次性**（私訊碼）、**公開**（社群共用碼，網頁抽籤不限次數；名額於 LINE 登記時認定） |
| 抽籤 | Apps Script 於「開放」之獎池項目中均等抽一項；排除該碼登錄之「已購項目」（可多項） |
| 結果頁 | 顯示抽中項目與**抽獎編號**，引導至官方 LINE 登記／預約 |
| 紀錄 | 每次抽籤寫入「抽獎紀錄」工作表，供人工核對與統計 |
| 後台（發碼） | Google 表單 A（發放付費碼）、B（建立公開碼）；程式產生抽獎碼並將抽獎連結寄至填寫者 Gmail；填寫者須在授權名單內 |
| 追蹤 | GA4 事件（前綴 `gacha_`；不含抽獎碼） |

### 2. MVP 明確不做

- 不加入導覽列、不開放搜尋引擎索引。
- **不做無碼抽獎**（任何人點進來即可抽）：無身分可識別、Apps Script 無法取得訪客 IP，無法防重抽；若日後需要，另立 DEC 作為獨立產品評估。
- 不做每日限量／隨機開放時段（流量不足時反效果，見第九節）。
- 不做機率加權、每月名額自動計算、過期自動判斷、加價購自動折抵——皆先人工處理。
- 不做會員、線上金流、與 LINE 帳號綁定。
- 不使用 VPS Node 服務與 AI。

### 3. 防護範圍（威脅模型）

本 MVP 為概念驗證，**名額與體驗之最終認定在人工（LINE＋表單 C）**；系統防護之目的在於避免一般誤用與輕度濫用影響其他使用者，而非抵禦蓄意攻擊。下表區分**系統防護**（程式保證）與**人工控管**（小編依流程核對，系統不保證）。設計審查以本小節為基準：落在「不防」範圍之情境，列為已知限制即可，不視為阻擋項目。

| | 情境 | 對應措施 |
| :--- | :--- | :--- |
| **要防** | 客人連點、重新整理、重複開啟連結 | 一次性碼冪等、鎖內複查（第六節） |
| **要防** | 一般訪客以無痕視窗重抽公開碼 | 不影響名額：名額於人工登記認定（第三節第 4 小節） |
| **要防** | 簡單腳本短時間灌入請求 | 進鎖前拒絕＋盡力而為之節流（第六節第 1 小節） |
| **要防** | 同一抽獎編號重複登記；誤填狀態導致受理時間錯置 | 系統防護：表單 C 拒絕重複、受理時間不可覆寫（第五節第 5 小節） |
| **要防** | 偽造或修改之截圖 | 人工控管：小編以抽獎編號查核「抽獎紀錄」（第三節第 4 小節） |
| **要防** | 同一 LINE 帳號以多組公開碼抽獎編號重複登記 | **人工控管**：小編於 LINE 端辨識；表單 C 只收抽獎編號與狀態，**系統無法辨識 LINE 帳號** |
| **要防** | 公開活動超額受理（例：名額 20 人卻受理第 21 位） | **人工控管**：小編受理前核對「抽獎紀錄」該碼已登記筆數與「活動名額」；活動名額僅供紀錄，**系統不阻擋** |
| **要防** | 一次性碼外流後由他人登記 | **人工控管**：小編確認抽獎編號係由**當初私訊該抽獎連結之 LINE 對話**傳回；表單 A 不記錄收件客人身分，**系統不保證** |
| **要防** | 抽獎碼經 GA4、伺服器紀錄外流 | 系統防護：fragment＋GA 載入前清除（第四節） |
| 不防 | 蓄意且持續之攻擊（大量併發耗盡 Apps Script 配額、刻意繞過節流） | 接受短暫無法使用；緊急時停用公開碼 |
| 不防 | 計數精確到筆之保證（快取提早失效時節流可能多放行一批） | 接受少量多餘紀錄 |
| 不防 | 秒級競態（例：業主於 Sheet 介面停用碼之同時，仍有請求完成抽籤） | 名額由人工認定，多出之紀錄不產生權益 |

- **系統層面之最壞結果**為多出若干無效抽籤紀錄或短暫無法抽籤；**系統本身不發出任何名額**（名額一律經人工受理），付費客人之結果亦不會遺失（冪等，可重試）。
- **人工控管風險**：重複登記、超額受理、冒用一次性碼之防範依賴小編依流程核對；人為疏失屬營運風險，MVP 接受，由第八節之流程與「抽獎紀錄」事後稽核降低。若實際發生頻率不可接受，再評估加入身分或名額之系統檢查（另立 DEC）。
- 實際數據顯示濫用超出上表時（例：重抽比例過高、腳本攻擊頻繁），另立 DEC 評估升級防護。

## 三、 商業規則（暫定，待業主確認）

### 1. 體驗內容

| 項目 | 暫定值 | 備註 |

| 老師報酬 | **暫無** | 日後由業主設立預算作為激勵與成本控制 |

依 `content_inventory.md` 第 2.2 節之服務項目，**八字命理除外**：

### 3. 升級路徑（加價購）

- **僅限抽中之項目**：抽中占星體驗者，可以優惠報名占星循環班；不提供「喜歡塔羅就直接拿塔羅課程優惠」之路徑——優惠只用在把客人帶進新領域。
- 形式建議為**課程首月固定金額折抵**（金額與期限待定，建議 200～300 元、體驗後 14～30 天內），不採加送時數（老師無報酬，不宜再增加負擔）。
- 無對應課程之項目（毛孩溝通）改為完整服務之折抵。
- MVP 由人工於 LINE 處理，結果頁只顯示固定說明文案。

### 4. 兩種抽獎碼

| | 一次性碼（私訊） | 公開碼（FB／Threads／IG） |
| :--- | :--- | :--- |
| 取得方式 | 付費客人於 LINE 完成付款後，由小編私訊連結 | 業主於社群貼文公布 |
| 一碼一人 | 是 | 否，多人共用 |
| 網頁抽籤次數 | 1 次（重複兌換回傳原結果） | **不限**（系統不扣名額） |
| 名額 | 1 人 | 由業主於貼文公布（例：前 20 位）；**以登記受理順序（該筆首次以表單 C 填寫狀態之順序）認定**，額滿後業主將碼改為停用 |
| 承諾 | **保證提供體驗** | **不保證**，依當月老師排班與量能安排 |
| 主要用途 | 兌現贈品、交叉銷售 | 流量來源統計、吸引加入官方 LINE 好友 |
| 去重 | 碼本身唯一 | 於 LINE 端人工處理：每個 LINE 帳號每個活動限登記一次 |

- **名額認定規則（公開碼）**：
  1. 排序依據為**登記受理順序**，即該筆抽獎紀錄**首次以表單 C 成功填寫任何狀態**之順序（紀錄中之「登記受理時間」；正常流程下首次填寫即為 `已登記`，誤填其他狀態亦以首次填寫時間為準）；**不是抽籤時間**（可藉重抽提前佔位），亦不另行記錄 LINE 訊息時間（須人工抄寫、易出錯）。小編依 LINE 訊息抵達順序逐筆受理，使兩者順序一致。
  2. 小編受理登記時，以抽獎編號於「抽獎紀錄」查核：編號存在、抽獎碼與抽中項目相符（截圖可被修改，不得只憑截圖）；同一抽獎編號只受理一次；同一 LINE 帳號每個活動只受理一次；受理前確認該碼已登記筆數未達活動名額（以上後兩項為人工控管，系統不檢查）。
  3. 受理後由小編以**表單 C** 將該筆紀錄之處理狀態改為 `已登記`；程式同時寫入「登記受理時間」（首次寫入後不再覆寫），使名額認定可事後稽核。額滿後業主將抽獎碼改為 `停用`，網頁即顯示「活動已結束」。
- **職責分層**：試算表負責「結果真偽」與統計；LINE 人工登記負責「名額歸屬」。系統不防重抽，名額之防護集中在人工登記層（理由見第十一節第 2 項）；但「不限抽籤次數」**不等於不限請求速率**——兌換端點仍有節流，避免試算表被無限寫入（第六節第 1 小節）。
- **已知限制（MVP 接受）**：同一人可於網頁重複抽籤（例：無痕視窗），挑選偏好項目後再登記。影響僅限於公開碼（本即不保證提供），且重抽行為會反映在「抽獎紀錄」之抽籤次數，可作為概念驗證之觀察數據；若重抽比例過高，再評估改為 claim token 或身分綁定。
- 公開碼之文案須避免「抽中贈送」等保證性用語，明示名額有限、依**登記受理順序**安排；建議準備保底選項（例：名額用完者改提供小額折抵）。文案由業主定稿。
- 「不定時發碼、限量先搶」之稀缺感改由貼文文案（例：「限前 20 位登記」）與手動停用碼營造；網頁不即時顯示剩餘名額。

## 四、 系統架構

```
訪客瀏覽器
  └─ GET  /gacha#code=XXXX            → nginx 直接回傳靜態 HTML（noindex；fragment 不送至伺服器）
  └─ JSONP GET <Apps Script URL>       → Google Apps Script（星靈扭蛋專用）
                                           【進鎖前檢查，不取鎖】
                                           1. 讀取抽獎碼表：碼存在、狀態為啟用（否則直接回錯誤）
                                           2. 一次性碼已有紀錄 → 直接回傳原結果（唯讀）
                                           3. 公開碼超過節流上限 → 直接回 RATE_LIMITED
                                           【鎖內】
                                           4. tryLock（公開碼短等待、一次性碼較長等待；逾時回 BUSY）
                                           5. 鎖內複查：重讀該碼最新資料（存在、類型、狀態、已購項目）、
                                              一次性碼是否已有紀錄、公開碼節流計數
                                           6. 讀取獎池設定（開放項目，排除已購項目）
                                           7. 均等抽一項 → 寫入抽獎紀錄（產生抽獎編號）→ 節流計數＋1
                                           8. 釋放鎖 → 回傳結果
```

官方發碼（後台）：

```
小編／業主手機
  └─ Google 表單 A／B／C 送出（收集已驗證之電子郵件）
       → 表單自動寫入各自之「表單回應」工作表
       → onFormSubmit 觸發器（同一 Apps Script 專案）
            1. 比對填寫者 email 是否在「授權名單」
            2. LockService 取得鎖 →
                 A／B：產生抽獎碼 → 寫入「抽獎碼」工作表
                 C：  依抽獎編號更新「抽獎紀錄」之處理狀態（首次由空白改為任何狀態時寫入登記受理時間）
               → 釋放鎖
            3. 寄送結果（抽獎連結、更新結果或失敗原因）至填寫者 Gmail
```

- 客人兌換（`doGet`）與官方發碼（`onFormSubmit`）為**同一個綁定於試算表之 Apps Script 專案**；兩者皆會寫入試算表，一律於 `LockService` 鎖內寫入。
- **抽獎連結使用網址 fragment（`#code=`）而非 query（`?code=`）**：fragment 不會送至伺服器（不進 nginx access log）。
- **GA 載入前擷取並清除抽獎碼**：GA4 之 `page_location` 預設為含 fragment 之 `location.href`，且 `Layout.astro` 於 `<head>` 即載入 `GoogleAnalytics` 並執行 `gtag('config')`；頁面本身之腳本執行較晚，來不及清除。故於 `Layout.astro` 之 `<GoogleAnalytics />` **之前**新增同步 inline script（寫法比照既有之主題初始化 script）：
  1. **僅於 `/gacha` 輸出**（以 `Astro.url.pathname` 於伺服器端條件渲染），其他頁面之 HTML 不變。
  2. 若 `location.hash` 為 `#code=…`：將碼存入 `sessionStorage`（try/catch 包覆），再以 `history.replaceState` 移除 fragment。
  3. `/gacha` 頁面腳本自 `sessionStorage` 讀取碼後即刪除；`sessionStorage` 無法使用時（例：隱私模式例外），inline script 改將碼暫存於 `window` 變數供頁面腳本讀取。
  - 理由與上一版之修正見第十一節第 7 項。
- 傳輸採 JSONP（DEC-067：行動裝置 fetch 被 Apps Script 302 跨網域轉址阻擋）。抽獎碼因此會出現在送往 Apps Script（Google）之請求網址中；碼為一次性或本即公開，且一次性碼之結果綁定於碼、重複兌換回傳同一結果；冒用者須經小編人工核對 LINE 對話方能登記（第二節第 3 小節，人工控管），風險可接受。
- 前端環境變數：`PUBLIC_GACHA_API_URL`（Apps Script web app URL，比照 `PUBLIC_WISHLIST_API_URL`）。未設定時之行為待定（見第十節）。
- **共用表面影響（實作時）**：`.env.example`（新增變數）、`AGENTS.md`（路由表、環境變數）、`demo_docs/content_inventory.md`（頁面標題、meta description、說明、結果頁與錯誤訊息文案，於業主定稿後登錄）；**`src/layouts/Layout.astro`（新增僅於 `/gacha` 輸出之 inline script，見上；全站共用表面變更，實作時須明確告知）**；不修改 `Navbar.astro`、`GoogleAnalytics.astro`、nginx、VPS 服務（`noindex` prop 已存在）。

| 表單 | 欄位（皆以表單內建驗證防呆） | 使用者 |
| :--- | :--- | :--- |
| **A. 發放付費碼** | 已購項目（核取方塊，可複選、可不選） | 小編 |

### 7. 避免表單與程式互相干擾

4. `onFormSubmit` 為可安裝觸發器，以建立者帳號身分執行；帳號移轉時須重建。

## 六、 Apps Script 介面（概念）

單一動作 `redeem(code)`，回應形狀待實作時定稿：

| 情境 | 回應 |
| :--- | :--- |
| 抽籤成功（含一次性碼重複兌換） | 抽中項目、抽獎編號、是否為重複兌換 |
| 碼不存在 | 錯誤：無效抽獎碼 |
| 碼已停用（含公開碼額滿後停用） | 錯誤：活動已結束 |
| 獎池無開放項目 | 錯誤：暫無可抽項目 |
| 排除已購項目後無可抽項目 | 錯誤（專屬代碼）：請洽官方 LINE |
| 公開碼超過節流上限 | 錯誤 `RATE_LIMITED`：抽太快了，請稍後再試（不影響名額） |
| 取鎖逾時 | 錯誤 `BUSY`：請稍後再試 |
| 其他 | 錯誤：請稍後再試 |

- **必做**：碼須隨機不可猜；一次性碼重複送出回傳**同一結果**（冪等，非錯誤）；所有寫入於 `LockService` 鎖內完成，鎖內以最新資料重讀該碼（存在、類型、狀態、已購項目）並複查一次性碼是否已有紀錄，避免連點造成重複抽籤、或以停用前之舊資料完成抽籤（許願池 DEC-035／039 之併發教訓）。
- 隨機數使用 Apps Script 伺服器端產生；不接受前端傳入任何影響結果之參數（如指定項目）。
- 客人兌換端點（`doGet`，匿名公開）**不得提供任何發碼或修改功能**；發碼與狀態更新只經表單觸發器（第五節第 5 小節）。

### 1. 節流與鎖策略（防止匿名端點無限寫入）

「公開碼不限抽籤次數」指**不以次數扣名額**，不代表不限請求速率。沿用許願池 v3 之 `CacheService` 計數模式（`course_wishlist_plan_v3.md`）：

| 層 | 做法 | 目的 |
| :--- | :--- | :--- |
| 進鎖前拒絕 | 無效碼、停用碼、一次性碼重複兌換（唯讀回傳）、公開碼已超過節流 → **不取鎖**直接回應 | 大量請求不排隊、不佔鎖，保護付費客人兌換與表單觸發器 |
| 公開碼節流 | 每個公開碼：短視窗上限（暫定 10 秒 10 次，比照許願池單課上限）＋每小時上限（暫定 200 次）；計數鍵含抽獎碼雜湊 | 腳本最多寫入有限筆數之紀錄；正常社群導流不被誤擋。數值實作時依實測調整 |
| 鎖內複查 | 進鎖後再檢查一次節流計數（進鎖前之檢查為近似值，可能被併發穿透） | 減少併發穿透；**屬盡力而為，非精確保證**（見下方已知限制） |
| 鎖等待分級 | `tryLock`：公開碼短等待（暫定 3 秒）、一次性碼較長等待（暫定 10 秒）；逾時回 `BUSY` | 尖峰時優先保住付費客人 |

- 被拒絕之請求不寫入試算表、不影響任何名額（名額本即於 LINE 認定）。
- 緊急處置：業主將該公開碼改為 `停用`，後續請求於進鎖前即被拒絕。
- **已知限制（MVP 接受）**：Apps Script 無法取得訪客 IP，無法針對單一來源限流；蓄意之大量併發仍可能耗盡 Apps Script 同時執行配額，造成短暫無法使用。屆時一次性碼客人可稍後重試（冪等，不會遺失結果），不影響名額認定。
- **已知限制（MVP 接受）**：`CacheService` 之存活時間僅為建議值，資料可能提早清除；計數遺失時節流可能多放行一批請求。節流目的在擋住大量灌入、而非精確限額（第二節第 3 小節），故不將計數改存試算表——每個請求多一次試算表讀寫，反而加重鎖之負擔。

## 七、 前端（`/gacha`）

- 由 `Layout.astro` 之 inline script 於 GA 載入前擷取 `#code=` 並清除網址（第四節）；頁面腳本自 `sessionStorage` 讀取後自動填入並刪除，訪客只需按下扭蛋按鈕。保留手動輸入框作為備用。
- `RATE_LIMITED`／`BUSY` 顯示友善之稍後再試訊息，不自動重送。
- 抽籤儀式動畫（形式待定；可參考抽卡頁之儀式感），`prefers-reduced-motion` 時略過。
- 結果頁：抽中項目、抽獎編號、「截圖並傳送至官方 LINE 登記」之指引與 LINE 連結（固定 URL，見 `AGENTS.md`）；公開碼另顯示「名額有限、依登記受理順序安排，抽中不代表已取得名額」說明。
- 公開碼：同一瀏覽器再次進入時直接顯示上次結果（localStorage，try/catch 包覆；只減少無心重複，不作為防濫用機制）。
- 無碼進入：顯示扭蛋說明與「如何取得抽獎碼」（文案待業主定稿）。
- 深淺雙模式、鍵盤操作、`aria-live`；GA 事件前綴 `gacha_`，不送出抽獎碼。

## 八、 營運流程

### 1. 付費客人（一次性碼）

1. 客人於 LINE 完成付款。
2. 小編以手機填寫表單 A（選擇已購項目）送出，於 Gmail 收到抽獎連結後複製私訊客人。
3. 客人點連結抽籤，截圖結果傳回 LINE。
4. 小編確認抽獎編號係由**當初私訊該抽獎連結之 LINE 對話**傳回，並依抽獎編號核對紀錄後，以表單 C 改為 `已登記`，安排 15 分鐘體驗並隨進度更新處理狀態；體驗後依升級路徑引導報名。

### 2. 社群活動（公開碼）

1. 業主填寫表單 B（活動代號、選填活動名額與自訂碼）建立公開碼，於 Gmail 收到後於社群貼文公布（貼文載明名額，例：限前 20 位登記）。
2. 訪客抽籤後加入官方 LINE、傳送抽獎編號登記。
3. 小編依 LINE 訊息抵達順序受理：以抽獎編號查核「抽獎紀錄」（第三節第 4 小節之名額認定規則）；每個 LINE 帳號每個活動只受理一次登記；受理後以表單 C 改為 `已登記`（程式寫入不可覆寫之登記時間）。
4. 達名額時業主將抽獎碼改為 `停用`；超額登記者依保底選項處理。

### 3. 量能調整

- 某項目當月忙不過來 → 「獎池設定」改為 `暫停`。
- 公開活動名額 → 由貼文公布、登記受理順序認定，額滿手動停用碼。

## 九、 已評估、暫不採用之方案

| 方案 | 不採用理由 |
| :--- | :--- |
| 抽中與否之抽獎（可能落空） | 付費客人落空會降低滿意度，與目標相反 → 改為必中、抽項目 |
| 演算法簽章碼（不需登錄即可驗證真偽） | 適用於大量發碼；本案發碼量小且每碼須記錄來源與已購項目 → 採**白名單制**：只有已登錄於「抽獎碼」工作表且狀態為啟用之碼有效 |
| 人工於試算表手打抽獎碼 | 非程式背景之團隊易打錯、重複或打成規律字串 → 由程式產生 |
| 試算表自訂選單（按鈕發碼） | Google 試算表手機 App 不支援自訂選單與對話框，小編多以手機作業 |
| 試算表 `onEdit`（填一列、程式補齊） | 可行，但小編須有試算表編輯權，防呆僅靠下拉選單與保護範圍 → 改用表單 |
| 自製 Apps Script 後台 Web App | 開發量較大；以擁有者身分執行時，一般 Gmail 帳號通常無法取得使用者 email，須另設管理密碼 → 表單之已驗證 email 較簡單 |
| 私訊碼、公開碼各一張工作表 | 欄位與邏輯重複，新增來源須再開表 → 改以「類型」欄位區分 |
| 加入導覽列 | 無碼訪客進入即為死路；導覽列已滿（DEC-082 之 1024px 考量） |
| 官網每日限量（隨機時段開放、每日上限 20 次）、無碼可抽 | 流量不足時計數器長期不動，反而暴露低流量；隨機時段需要既有主動回訪受眾；無身分無法防重抽；贈品為老師無償時間，對匿名大眾開放無成本上限 → 改以「公開碼＋貼文公布名額」於社群製造稀缺感 |
| 以 VPS Node 服務＋資料庫實作 | 違反 AI 功能「不保存使用者內容」之架構原則、增加維運；試算表讓兼職團隊可直接管理 |

### 1. 抽獎碼進入 GA4（採納主要建議）

> **v0.3 更正**：本項「fragment＋頁面腳本 `replaceState`」不足以保證碼不進 GA4，已改為於 `Layout.astro` GA 載入前處理，見第 7 項。

- 審查所述屬實：`GoogleAnalytics.astro` 之 `gtag('config', id)` 會自動送出含完整網址之 page_view；query 亦會進入 nginx access log。
- 風險評估：GA 僅開發者本人存取，nginx log 須取得 VPS 權限才能讀取；且一次性碼之結果綁定於碼、重複兌換回傳同一結果，冒用者取得碼亦無法搶走客人權益（實際兌換須於 LINE 登記，小編知道該碼私訊給誰）。故判定為**低風險**。
- 處理：採審查建議之 fragment（`#code=`），前端讀取後 `replaceState` 清除——成本極低、可同時避開伺服器紀錄。
- 未採納：審查之替代方案「修改 GA 元件送出手動 page_view」。考量 GA4 是否保留 fragment、`<head>` 中 config 與頁面腳本之執行先後無法百分之百保證，此方案可作為加強；但會動到全站共用元件，與上述低風險評估不成比例，故 MVP 不做。日後若 GA 開放他人存取，再評估。

### 2. 公開碼名額耗盡（採納並延伸）

- 審查所述屬實，且實際門檻比「批量腳本」更低：一般訪客以無痕視窗重整即可重抽，並可藉此**挑選偏好項目**（審查未提及，會削弱「把客人帶進新領域」之交叉銷售設計）。
- 討論過程：初期全人工審查，批量腳本可由「抽獎紀錄」之時間戳記輕易識別；但若名額於抽籤時扣減，**識別發生在事後，傷害（後續真實訪客看到額滿）已即時發生**。真正的負面影響是使用者體驗，而非資料安全。
- 處理：採審查之第一方案——「抽出結果」與「取得資格」分開。網頁抽籤**不限次數、不扣名額**；名額以客人將抽獎編號傳至 LINE 之順序（FIFO）認定，小編以抽獎編號查核試算表真偽，額滿後手動停用碼。如此重抽與腳本皆不會影響其他訪客。

### 7. GA 記錄碼（採納；更正 v0.2 之判斷）

- 審查所述屬實：`Layout.astro` 於 `<head>` 載入 `GoogleAnalytics` 並立即 `gtag('config')`，而 `/gacha` 頁面腳本於文件解析後才執行；GA4 `page_location` 預設含 fragment，故 v0.2「頁面腳本 `replaceState`」無法保證碼不進 GA4。v0.2 第十一節第 1 項「以 fragment 處理即可」之判斷有誤，於此更正（審查者亦更正了其上一輪之 fragment 建議）。
- 處理：採審查之修正方式——於 `Layout.astro` 之 `<GoogleAnalytics />` 前同步擷取碼、存入 `sessionStorage`、移除網址。補充兩點：inline script 以伺服器端條件**僅於 `/gacha` 輸出**，使其他頁面 HTML 完全不變；`sessionStorage` 例外時以 `window` 變數備援。
- 取捨：此為全站共用表面之變更（AGENTS.md 規定須明確告知），已更新第四節影響清單。仍不修改 `GoogleAnalytics.astro`（見第九節）。
- 風險評估維持不變（GA 僅開發者存取、一次性碼外流影響有限）；採納理由是修正成本小、範圍明確，且可閉合此項。

### 8. 匿名端點無限寫入（採納）

- 審查所述屬實：v0.2「不限抽籤次數」使每次公開碼請求皆取鎖並新增一列，無速率限制；大量併發可造成垃圾紀錄、鎖逾時，連帶阻塞付費客人兌換與表單發碼。開發者亦同意：初期人工審查雖可從時間戳記識別腳本，但寫入與鎖阻塞之傷害於當下即發生。
- 處理：釐清「不限抽籤次數」＝不以次數扣名額，**不等於不限請求速率**。沿用許願池 v3 已驗證之 `CacheService` 計數模式，並依審查建議採短等待鎖；另加入審查未提及之兩點：
  1. **進鎖前拒絕**：無效碼、停用碼、超過節流者，以及一次性碼之重複兌換（唯讀）皆不取鎖，使大量請求不排隊。
  2. **鎖等待分級**：公開碼短等待、一次性碼較長等待，尖峰時優先保住付費客人。
- 節流回傳 `RATE_LIMITED`、取鎖逾時回 `BUSY`，皆不影響名額。數值暫定，實作時依實測調整（第十節）。
- 已知限制：Apps Script 無法取得 IP，無法防止蓄意耗盡同時執行配額；MVP 接受，緊急時停用該公開碼。

### 9. 名額稽核（採納並延伸）

- 審查建議於抽獎碼保留活動名額、於抽獎紀錄新增不可覆寫之 LINE 登記時間，採納。抽獎碼之「活動名額」僅供紀錄，不據以限制抽籤（不回到 v0.1 之扣名額設計）。
- 延伸：v0.2 規定小編對試算表僅有檢視權，若登記時間須人工填寫，只能由業主代填或開放編輯權（後者使登記時間可被覆寫、失去稽核意義）。故將**表單 C（更新處理狀態）由可選改為 MVP 必做**：程式於首次 `已登記` 時寫入登記時間與登記人，之後不覆寫；同一編號重複登記時拒絕並寄信提醒，兼作「同一抽獎編號只受理一次」之系統防呆。
- 登記時間採表單送出時間，而非 LINE 訊息抵達時間（後者無法自動取得）；小編依 LINE 訊息順序逐筆受理，兩者順序一致即可。

### 10. 鎖內重讀碼狀態（採納）

- 鎖內本已複查一次性碼紀錄，順帶重讀該碼列（存在、類型、狀態、已購項目）成本極低，故採納。
- 實際影響評估：業主停用碼之後數秒內多完成一筆抽籤，名額仍由人工認定，不產生任何權益——依防護範圍屬「不防」之秒級競態。審查另建議記錄 Sheet 介面修改之非原子窗口，已併入防護範圍表之「秒級競態」一列，不另立說明。

### 11. CacheService 非精確保證（採納問題、不採納修法）

- 審查所述屬實（Google 文件說明快取存活時間僅為建議、可能提早淘汰）。問題根源在 v0.3 措辭「確保上限實際有效」過度承諾，已改為「盡力而為」並列入已知限制。
- 不採納「計數改存試算表或專用節流表」：節流之目的為擋住大量灌入，而非精確限額；改存試算表會使每個請求（含被拒絕者）多一次試算表讀寫並須持鎖，反而擴大審查第 8 項所擔心之鎖阻塞面。快取遺失之最壞結果為多出一批無效紀錄，屬防護範圍之「不防」。許願池以同一模式於線上運作至今。

### 12. 表單 C 狀態轉移（採納核心）

- 審查指出之實質漏洞：小編誤填 `已體驗` 後補 `已登記`，登記時間將被寫成較晚時間，破壞名額稽核。修正為：**首次由空白改為任何狀態時即寫入登記受理時間**，之後不覆寫；狀態不得改回空白；狀態值由表單下拉選單限定。
- 不採納嚴格單向轉移（禁止跳級、倒退）：兼職小編填錯時將無法自行修正，須管理者進試算表處理；而稽核所需之時間點已不可覆寫，處理歷程之細節（中間狀態）非名額認定所需。

### 13. FIFO 排序依據（採納第二方案）

- 審查所述屬實：v0.3 規則以 LINE 訊息時間排序，卻保存表單送出時間，兩者不一致。
- 採審查之第二方案：規則改為**以登記受理順序（表單 C 成功送出之順序）認定**，對外文案同步改為「依登記受理順序」。不採第一方案（新增 LINE 原始訊息時間欄位），因須小編人工抄寫、易出錯，反而降低可稽核性。小編依 LINE 訊息順序逐筆受理，實務上兩者順序差異極小。
- 欄位名稱「LINE 登記時間」改為「登記受理時間」，以符合實際記錄內容。

### 審查基準說明（給後續審查者）

- 請以第二節第 3 小節之防護範圍判斷意見之嚴重度：落在「不防」範圍、且不影響名額認定或付費客人權益之情境，建議標示為已知限制或 P3，而非阻擋項目。
- 若認為防護範圍本身劃定不當（例：某「不防」情境實際會造成權益損失），歡迎直接針對該表提出意見。

### 14. 排序事件定義（採納）

- v0.4 自身矛盾：規則寫「首次送出 `已登記` 之順序」，程式卻於「首次填寫任何狀態」時寫入受理時間。審查之例：A 於 10:00 誤填 `已預約`、B 於 10:01 填 `已登記`、A 於 10:02 改為 `已登記`——依記錄 A 先、依規則 B 先。
- 修正：受理順序統一定義為「**首次以表單 C 成功填寫任何狀態**」，與記錄一致；誤填者以首次填寫時間為準（小編誤填之當下即已受理該筆）。

### 15. 系統防護與人工控管之區分（採納第一選項）

- 審查所述屬實：表單 C 只收抽獎編號與狀態，無法辨識同一 LINE 帳號之多組編號、無法阻擋超額受理（活動名額僅供紀錄）；表單 A 不記錄收件客人，一次性碼之防冒用實係小編核對 LINE 對話。v0.4「不會有人因系統漏洞多取得名額」之說法高估系統能力。
- 處理：防護範圍表逐項標示**系統防護**或**人工控管**；「最壞結果」改為「系統本身不發出名額」，人工疏失另列為營運風險；第三節與第八節寫明小編之核對步驟（同一 LINE 帳號、名額筆數、一次性碼須由原私訊對話傳回）。
- 不採第二選項（加入身分或名額系統檢查）：與 MVP「名額由人工把關」之定位一致，待實際發生頻率不可接受時另立 DEC。
