> **帳號歸屬**：MVP 之試算表、表單、Apps Script 皆建立於**開發者帳號**下；確認使用效果良好後，再評估移轉至官方帳號（屆時須於新帳號重建觸發器）。

## 一、 設計原則

1. **抽的是「哪一項」，不是「有沒有」**：持私訊碼之付費客人必定獲得一項體驗，抽籤只決定項目——付費客人不會落空。
2. **伺服器決定結果**：抽籤由 Apps Script 執行並寫入試算表；前端只負責儀式動畫，不決定結果、無法重抽（同 `ai_platform_plan.md` 第一節第 3 條之精神）。
3. **骨架穩定、規則外置**：資料模型固定為「抽獎碼 → 抽獎紀錄」；獎池、名額、碼的啟用與否皆由業主於試算表調整，不需改程式或重新部署。
4. **依實體分表，不依來源分表**：私訊碼與公開碼為同一實體（抽獎碼）之不同「類型」，以欄位區分；新增發碼來源＝新增一種欄位值，不新增工作表。
5. **一個功能一個試算表檔案**：星靈扭蛋使用獨立試算表與獨立 Apps Script，與許願池互不影響（故障、權限、部署各自隔離）。
6. **機率不加權**：獎池中「開放」之項目均等機率。
7. **不捏造內容**：結果頁、說明頁與活動貼文文案由業主定稿；規格書與程式中之文案皆為佔位。
8. **系統管結果真偽，人工管名額歸屬**：試算表負責「抽籤結果是否為真」與統計；名額、身分、資格一律由小編於 LINE 受理時認定。系統本身不發出任何名額。

## 二、 範疇

### 1. MVP 包含

| 項目 | 說明 |
| :--- | :--- |
| 頁面 | `/gacha` 單頁（靜態），**`noindex`、不加入導覽列**（比照 `/tarot`）；深淺雙模式、行動裝置優先 |
| 入口 | LINE 私訊之抽獎連結、社群貼文之公開碼；有公開活動時可另以首頁輪播海報導入（DEC-086 既有機制） |
| 抽獎碼 | 兩種類型：**一次性**（私訊碼）、**公開**（社群共用碼，網頁抽籤不限次數；名額於 LINE 登記時認定） |
| 抽籤 | Apps Script 於「開放」之獎池項目中均等抽一項；排除該碼登錄之「已購項目」（可多項） |
| 結果頁 | 顯示抽中項目與**抽獎編號**，引導至官方 LINE 登記／預約 |
| 紀錄 | 每次抽籤寫入「抽獎紀錄」工作表，供人工核對與統計 |
| 後台 | Google 表單 A（發放付費碼）、B（建立公開碼）、C（更新處理狀態）；程式產生抽獎碼並將結果寄至填寫者 Gmail；填寫者須在授權名單內 |
| 追蹤 | GA4 事件（前綴 `gacha_`；不含抽獎碼） |

### 2. MVP 明確不做

- 不加入導覽列、不開放搜尋引擎索引。
- **不做無碼抽獎**（任何人點進來即可抽）：無身分可識別、Apps Script 無法取得訪客 IP，無法防重抽；若日後需要，另立 DEC 作為獨立產品評估。
- 不做每日限量／隨機開放時段。
- 不做機率加權、每月名額自動計算、過期自動判斷、加價購自動折抵——皆先人工處理。
- 不做會員、線上金流、與 LINE 帳號綁定。
- 不使用 VPS Node 服務與 AI。

各項之理由見第九節。

### 3. 防護範圍（威脅模型）

系統防護之目的在於避免一般誤用與輕度濫用影響其他使用者，而非抵禦蓄意攻擊。下表區分**系統防護**（程式保證）與**人工控管**（小編依流程核對，系統不保證）。**實作與審查皆以本小節為基準**：落在「不防」範圍、且不影響名額認定或付費客人權益之情境，列為已知限制，不另加防護。

| | 情境 | 類別 | 對應措施 |
| :--- | :--- | :--- | :--- |
| **要防** | 客人連點、重新整理、重複開啟連結 | 系統 | 一次性碼冪等、鎖內複查（第六節） |
| **要防** | 一般訪客以無痕視窗重抽公開碼 | 系統 | 抽籤不扣名額，重抽不影響他人（第三節第 4 小節） |
| **要防** | 簡單腳本短時間灌入請求 | 系統 | 進鎖前拒絕＋盡力而為之節流（第六節第 1 小節） |
| **要防** | 同一抽獎編號重複登記；誤填狀態導致受理時間錯置 | 系統 | 表單 C 拒絕重複之 `已登記`、受理時間不可覆寫（第五節第 5 小節） |
| **要防** | 抽獎碼經 GA4、伺服器紀錄外流 | 系統 | fragment＋GA 載入前清除（第四節） |
| **要防** | 他人猜得有效抽獎編號後搶先登記 | 系統 | 抽獎編號以密碼學安全之亂數產生（第六節） |
| **要防** | 備註文字被試算表當作公式執行 | 系統 | 自由文字強制為純文字（第五節第 5 小節） |
| **要防** | 偽造或修改之截圖 | 人工 | 小編以抽獎編號查核「抽獎紀錄」，不得只憑截圖 |
| **要防** | 同一 LINE 帳號以多組抽獎編號重複登記 | 人工 | 小編於 LINE 端辨識；表單 C 只收抽獎編號與狀態，系統無法辨識 LINE 帳號 |
| **要防** | 公開活動超額受理（例：名額 20 人卻受理第 21 位） | 人工 | 小編受理前核對該碼已登記筆數與「活動名額」；活動名額僅供紀錄，系統不阻擋 |
| **要防** | 一次性碼外流後由他人登記 | 人工 | 小編確認抽獎編號係由**當初私訊該抽獎連結之 LINE 對話**傳回；表單 A 之備註僅供查詢，不作為核對依據 |
| **要防** | 管理者手動修正時誤改「登記受理時間」「登記人」 | 人工 | 規定不得手動修改；誤改時以試算表編輯記錄查回原值（第五節第 6 小節） |
| 不防 | 蓄意且持續之攻擊（大量併發耗盡 Apps Script 配額、刻意繞過節流） | — | 接受短暫無法使用；緊急時停用公開碼 |
| 不防 | 計數精確到筆之保證（快取提早失效時節流可能多放行一批） | — | 接受少量多餘紀錄 |
| 不防 | 秒級競態（例：業主於試算表停用碼之同時，仍有請求完成抽籤） | — | 多出之紀錄不產生權益 |

- **系統層面之最壞結果**為多出若干無效抽籤紀錄或短暫無法抽籤；付費客人之結果不會遺失（冪等，可重試）。
- **人工控管風險**：重複登記、超額受理、冒用一次性碼之防範依賴小編依流程核對；人為疏失屬營運風險，MVP 接受，由第八節之流程與「抽獎紀錄」事後稽核降低。
- 實際數據顯示濫用或人為疏失超出可接受範圍時（例：重抽比例過高、腳本攻擊頻繁、重複受理頻傳），另立 DEC 評估加入身分或名額之系統檢查。

### 3. 升級路徑（加價購）

- **僅限抽中之項目**：抽中占星體驗者，可以優惠報名占星循環班；不提供「喜歡塔羅就直接拿塔羅課程優惠」之路徑——優惠只用在把客人帶進新領域。
- 形式建議為**課程首月固定金額折抵**（金額與期限待定，建議 200～300 元、體驗後 14～30 天內），不採加送時數（老師無報酬，不宜再增加負擔）。
- 無對應課程之項目改為完整服務之折抵。
- 以上金額與期限皆為建議；**業主確認並登錄 `content_inventory.md` 前，不得作為小編對客人之實際承諾**。
- MVP 由人工於 LINE 處理，結果頁只顯示固定說明文案。

### 4. 兩種抽獎碼

| | 一次性碼（私訊） | 公開碼（FB／Threads／IG） |
| :--- | :--- | :--- |
| 取得方式 | 付費客人於 LINE 完成付款後，由小編私訊連結 | 業主於社群貼文公布 |
| 一碼一人 | 是 | 否，多人共用 |
| 網頁抽籤次數 | 1 次（重複兌換回傳原結果） | **不限**（系統不扣名額） |
| 名額 | 1 人 | 由業主於貼文公布（例：前 20 位）；**依登記受理順序認定**，額滿後業主將碼改為停用 |
| 承諾 | **保證提供體驗** | **不保證**，依當月老師排班與量能安排 |
| 主要用途 | 兌現贈品、交叉銷售 | 流量來源統計、吸引加入官方 LINE 好友 |
| 去重 | 碼本身唯一 | 於 LINE 端人工處理：每個 LINE 帳號每個活動限登記一次 |

**名額認定規則（公開碼）**：

1. **登記受理順序**＝各筆抽獎紀錄之「登記受理時間」先後，即該筆**首次以表單 C 成功填寫任何狀態**之時間（正常流程下首次填寫即為 `已登記`；誤填其他狀態亦以首次填寫為準，因小編誤填之當下即已受理該筆）。**不採抽籤時間**（可藉重抽提前佔位），亦不另行記錄 LINE 訊息時間。小編依 LINE 訊息抵達順序逐筆受理，使兩者順序一致。
2. 小編受理時須核對四項：
   - 抽獎編號存在於「抽獎紀錄」，且抽獎碼與抽中項目相符（截圖可被修改，不得只憑截圖）。
   - 同一抽獎編號只受理一次（表單 C 會拒絕重複，系統防護）。
   - 同一 LINE 帳號每個活動只受理一次（人工控管）。
   - 該碼已登記筆數未達活動名額（人工控管）。
3. 受理後由小編以表單 C 將該筆改為 `已登記`。額滿後業主將抽獎碼改為 `停用`，網頁即顯示「活動已結束」。

**其他規則**：

- 「不限抽籤次數」指不以次數扣名額，**不等於不限請求速率**——兌換端點仍有節流（第六節第 1 小節）。
- **已知限制（MVP 接受）**：同一人可於網頁重複抽籤（例：無痕視窗），挑選偏好項目後再登記，削弱「帶進新領域」之設計。影響僅限於公開碼（本即不保證提供）；「抽籤次數」與「已登記數」之差距即反映重抽與未登記比例，作為概念驗證之觀察數據。
- 公開碼之文案須避免「抽中贈送」等保證性用語，明示名額有限、依**登記受理順序**安排；建議準備保底選項（例：名額用完者改提供小額折抵）。文案由業主定稿。
- 稀缺感由貼文文案（例：「限前 20 位登記」）與手動停用碼營造；網頁不即時顯示剩餘名額。

## 四、 系統架構

客人兌換：

```
訪客瀏覽器
  └─ GET  /gacha#code=XXXX            → nginx 直接回傳靜態 HTML（noindex；fragment 不送至伺服器）
  └─ JSONP GET <Apps Script URL>       → Google Apps Script（星靈扭蛋專用）
                                           【進鎖前檢查，不取鎖】
                                           1. 讀取抽獎碼表：碼存在、狀態為啟用（否則直接回錯誤）
                                           2. 一次性碼已有紀錄 → 直接回傳原結果（唯讀）
                                           3. 公開碼超過節流上限 → 直接回 RATE_LIMITED
                                           【鎖內】
                                           4. tryLock（公開碼短等待、一次性碼較長等待；逾時回 BUSY）
                                           5. 鎖內複查：重讀該碼最新資料（存在、類型、狀態、已購項目）、
                                              一次性碼是否已有紀錄、公開碼節流計數
                                           6. 讀取獎池設定（開放項目，排除已購項目）
                                           7. 均等抽一項 → 寫入抽獎紀錄（產生抽獎編號）→ 節流計數＋1
                                           8. 釋放鎖 → 回傳結果
```

官方後台：

```
小編／業主手機
  └─ Google 表單 A／B／C 送出（收集已驗證之電子郵件）
       → 表單自動寫入各自之「表單回應」工作表
       → onFormSubmit 觸發器（同一 Apps Script 專案）
            1. 比對填寫者 email 是否在「授權名單」
            2. LockService 取得鎖 →
                 A／B：產生抽獎碼 → 寫入「抽獎碼」工作表
                 C：  依抽獎編號更新「抽獎紀錄」之處理狀態
               → 釋放鎖
            3. 寄送結果（抽獎連結、更新結果或失敗原因）至填寫者 Gmail
```

- 客人兌換（`doGet`）與官方後台（`onFormSubmit`）為**同一個綁定於試算表之 Apps Script 專案**；兩者皆會寫入試算表，一律於 `LockService` 鎖內寫入。
- **抽獎連結使用網址 fragment（`#code=`）而非 query（`?code=`）**：fragment 不會送至伺服器（不進 nginx access log）。
- **GA 載入前擷取並清除抽獎碼**：GA4 之 `page_location` 預設為含 fragment 之 `location.href`，且 `Layout.astro` 於 `<head>` 即載入 `GoogleAnalytics` 並執行 `gtag('config')`；頁面本身之腳本執行較晚，來不及清除。故於 `Layout.astro` 之 `<GoogleAnalytics />` **之前**新增同步 inline script（寫法比照既有之主題初始化 script）：
  1. **僅於 `/gacha` 輸出**（以 `Astro.url.pathname` 於伺服器端條件渲染），其他頁面之 HTML 不變。
  2. 若 `location.hash` 為 `#code=…`：將碼存入 `sessionStorage`（try/catch 包覆），再以 `history.replaceState` 移除 fragment。
  3. `/gacha` 頁面腳本自 `sessionStorage` 讀取碼後即刪除；`sessionStorage` 無法使用時（例：隱私模式例外），inline script 改將碼暫存於 `window` 變數供頁面腳本讀取。
- 傳輸採 JSONP（DEC-067：行動裝置 fetch 被 Apps Script 302 跨網域轉址阻擋）。抽獎碼因此會出現在送往 Apps Script（Google）之請求網址中；碼為一次性或本即公開，且一次性碼之結果綁定於碼、重複兌換回傳同一結果，冒用者仍須經小編核對 LINE 對話方能登記，風險可接受。
- 前端環境變數：`PUBLIC_GACHA_API_URL`（Apps Script web app URL，比照 `PUBLIC_WISHLIST_API_URL`）。未設定時之行為待定（第十節第 2 小節）。
- **共用表面影響（實作時）**：
  - **`src/layouts/Layout.astro`**——新增僅於 `/gacha` 輸出之 inline script；全站共用表面變更，實作時須明確告知。
  - `.env.example`（新增變數）、`AGENTS.md`（路由表、環境變數）。
  - `demo_docs/content_inventory.md`——頁面標題、meta description、說明、結果頁與錯誤訊息文案，於業主定稿後登錄。
  - 不修改 `Navbar.astro`、`GoogleAnalytics.astro`、nginx、VPS 服務（`noindex` prop 已存在）。

- **備註之使用提醒**：僅寫暱稱、訂單編號或處理筆記；**不得填寫電話、地址等敏感個資**。表單 B 不設備註（使用者為業主，可直接編輯抽獎碼之備註欄）。

**表單 A（一次性碼）**：

- 自動帶入：類型 `一次性`、活動代號 `purchase`、狀態 `啟用`；程式產生抽獎碼並確認不與既有碼重複。

**表單 B（公開碼）**：

- 自訂碼留白則由程式隨機產生；自訂碼與既有碼重複時不建立並寄信通知。
- 「活動名額」僅寫入紀錄供事後稽核。

**表單 C（更新處理狀態）**：

| 情形 | 處理 |
| :--- | :--- |
| 抽獎編號不存在 | 不更新，寄信說明 |
| 該筆尚無登記受理時間（首次填寫任何狀態，含誤填） | 寫入處理狀態、登記受理時間、登記人 |
| 已有登記受理時間，送出 `已登記` | **拒絕，處理狀態不變**，寄信提醒「此編號已於 ○○ 受理」 |
| 已有登記受理時間，送出其他狀態 | 只更新處理狀態；登記受理時間與登記人不變 |

- 備註於更新成功時追加；被拒絕或編號不存在時不寫入（原始內容仍留於表單回應工作表）。
- 回信附抽獎碼與抽中項目，供小編與客人截圖二次核對。

### 6. 權限與分工

| 角色 | 工具 | 試算表權限 |
| :--- | :--- | :--- |
| 小編 | 表單 A、C、Gmail、LINE | 僅檢視 |
| 業主／管理者 | 表單 B；直接編輯獎池設定、授權名單、抽獎碼之狀態與備註；例外修正抽獎紀錄之「處理狀態」 | 可編輯 |
| 客人 | 官網 `/gacha` | 無 |

- **管理者例外修正**：表單 C 無法處理之情形（例：首次誤填 `已體驗`，之後須改為 `已登記`——表單 C 會拒絕），由管理者直接於試算表修改該筆之「處理狀態」。小編遇此情形回報管理者。
- **「登記受理時間」與「登記人」不得手動修改**（名額稽核依據）。MVP 不設保護範圍，屬人工控管。
- 修正歷程以 Google 試算表內建之**編輯記錄**追溯（儲存格右鍵「顯示編輯記錄」或版本記錄）；修正原因於內部 LINE 群組告知即可。

### 7. 避免表單與程式互相干擾

1. 表單只寫入各自之「表單回應」工作表；程式**只讀取、不修改**回應工作表，正式資料寫入抽獎碼與抽獎紀錄工作表——兩者寫入範圍不重疊。
2. 程式依**欄位標題**讀取回應，不依欄位位置（表單題目增修後欄位順序可能改變）。
3. 回應工作表不得手動插欄、刪列或排序（寫入說明分頁）。
4. `onFormSubmit` 為可安裝觸發器，以建立者帳號身分執行；帳號移轉時須重建。

## 六、 Apps Script 介面（概念）

單一動作 `redeem(code)`，回應形狀待實作時定稿：

| 情境 | 回應 |
| :--- | :--- |
| 抽籤成功（含一次性碼重複兌換） | 抽中項目、抽獎編號、是否為重複兌換 |
| 碼不存在 | 錯誤：無效抽獎碼 |
| 碼已停用（含公開碼額滿後停用） | 錯誤：活動已結束 |
| 獎池無開放項目 | 錯誤：暫無可抽項目 |
| 排除已購項目後無可抽項目 | 錯誤（專屬代碼）：請洽官方 LINE |
| 公開碼超過節流上限 | 錯誤 `RATE_LIMITED`：抽太快了，請稍後再試（不影響名額） |
| 取鎖逾時 | 錯誤 `BUSY`：請稍後再試 |
| 其他 | 錯誤：請稍後再試 |

**必做**：

- **冪等**：一次性碼重複送出回傳**同一結果**，非錯誤。
- **鎖內寫入與複查**：所有寫入於 `LockService` 鎖內完成；鎖內以最新資料重讀該碼（存在、類型、狀態、已購項目）並複查一次性碼是否已有紀錄，避免連點造成重複抽籤、或以停用前之舊資料完成抽籤（許願池 DEC-035／039 之併發教訓）。
- **結果由伺服器決定**：不接受前端傳入任何影響結果之參數（如指定項目）。
- **密碼學安全之亂數**：抽獎碼（程式產生者）與抽獎編號皆以 `Utilities.getUuid()`（UUID v4）所含之隨機位元為來源，轉換為指定字元集；**不得使用 `Math.random()`**，亦不得以時間戳記或流水號衍生（Apps Script 無 `crypto` 模組；精神比照 `tarot_plan.md` 之 `crypto.randomInt`）。
- **撞號重新產生**：轉換為短碼後可能撞號。抽獎碼與抽獎編號皆於鎖內比對既有資料，重複即重新產生，直到不重複為止。
- **匿名端點唯讀於管理面**：`doGet` 不得提供任何發碼或修改功能；發碼與狀態更新只經表單觸發器。

### 1. 節流與鎖策略（防止匿名端點無限寫入）

沿用許願池 v3 之 `CacheService` 計數模式（`course_wishlist_plan_v3.md`）：

| 層 | 做法 | 目的 |
| :--- | :--- | :--- |
| 進鎖前拒絕 | 無效碼、停用碼、一次性碼重複兌換（唯讀回傳）、公開碼已超過節流 → **不取鎖**直接回應 | 大量請求不排隊、不佔鎖，保護付費客人兌換與表單觸發器 |
| 公開碼節流 | 每個公開碼：短視窗上限（暫定 10 秒 10 次，比照許願池單課上限）＋每小時上限（暫定 200 次）；計數鍵含抽獎碼雜湊 | 腳本最多寫入有限筆數之紀錄；正常社群導流不被誤擋 |
| 鎖內複查 | 進鎖後再檢查一次節流計數（進鎖前之檢查為近似值，可能被併發穿透） | 減少併發穿透；**屬盡力而為，非精確保證** |
| 鎖等待分級 | `tryLock`：公開碼短等待（暫定 3 秒）、一次性碼較長等待（暫定 10 秒）；逾時回 `BUSY` | 尖峰時優先保住付費客人 |

- 被拒絕之請求不寫入試算表、不影響任何名額。
- 緊急處置：業主將該公開碼改為 `停用`，後續請求於進鎖前即被拒絕。
- 數值皆為暫定，實作時依實測調整。
- **已知限制（MVP 接受）**：
  - Apps Script 無法取得訪客 IP，無法針對單一來源限流；蓄意之大量併發仍可能耗盡同時執行配額，造成短暫無法使用。一次性碼客人可稍後重試，不會遺失結果。
  - `CacheService` 之存活時間僅為建議值，資料可能提早清除；計數遺失時節流可能多放行一批請求。節流目的在擋住大量灌入、而非精確限額。

## 七、 前端（`/gacha`）

- 抽獎碼由 `Layout.astro` 之 inline script 擷取（第四節）；頁面腳本讀取後自動填入，訪客只需按下扭蛋按鈕。保留手動輸入框作為備用。
- `RATE_LIMITED`／`BUSY` 顯示友善之稍後再試訊息，不自動重送。
- 抽籤儀式動畫（形式待定；可參考抽卡頁之儀式感），`prefers-reduced-motion` 時略過。
- 結果頁：抽中項目、抽獎編號、「截圖並傳送至官方 LINE 登記」之指引與 LINE 連結（固定 URL，見 `AGENTS.md`）；公開碼另顯示「名額有限、依登記受理順序安排，抽中不代表已取得名額」說明。
- 公開碼：同一瀏覽器再次進入時直接顯示上次結果（localStorage，try/catch 包覆；只減少無心重複，不作為防濫用機制）。
- 無碼進入：顯示扭蛋說明與「如何取得抽獎碼」（文案待業主定稿）。
- 深淺雙模式、鍵盤操作、`aria-live`；GA 事件前綴 `gacha_`，不送出抽獎碼。

## 八、 營運流程

### 1. 付費客人（一次性碼）

1. 客人於 LINE 完成付款。
2. 小編以手機填寫表單 A（選擇已購項目）送出，於 Gmail 收到抽獎連結後複製私訊客人。
3. 客人點連結抽籤，截圖結果傳回 LINE。
4. 小編確認抽獎編號係由**當初私訊該抽獎連結之 LINE 對話**傳回，並依抽獎編號核對紀錄後，以表單 C 改為 `已登記`。
5. 安排體驗（時長暫定 15 分鐘），隨進度以表單 C 更新處理狀態；體驗後依升級路徑引導報名。

### 2. 社群活動（公開碼）

1. 業主填寫表單 B 建立公開碼，於 Gmail 收到後於社群貼文公布（貼文載明名額，例：限前 20 位登記）。
2. 訪客抽籤後加入官方 LINE、傳送抽獎編號登記。
3. 小編依 LINE 訊息抵達順序逐筆受理：依第三節第 4 小節之名額認定規則核對後，以表單 C 改為 `已登記`。
4. 達名額時業主將抽獎碼改為 `停用`；超額登記者依保底選項處理。

### 3. 量能調整

- 某項目當月忙不過來 → 「獎池設定」改為 `暫停`。
- 公開活動名額 → 由貼文公布、依登記受理順序認定，額滿手動停用碼。

| 抽中與否之抽獎（可能落空） | 付費客人落空會降低滿意度，與目標相反 → 改為必中、抽項目 |
| 資格限於「只購買一種服務之客人」 | 增加小編判斷負擔 → 改以已購項目多選排除 |
| 加入導覽列 | 無碼訪客進入即為死路；導覽列已滿（DEC-082 之 1024px 考量） |
| 官網每日限量（隨機時段開放、每日上限 20 次）、無碼可抽 | 流量不足時計數器長期不動，反而暴露低流量；隨機時段需要既有主動回訪受眾；無身分無法防重抽；贈品為老師無償時間，對匿名大眾開放無成本上限 → 改以「公開碼＋貼文公布名額」於社群製造稀缺感 |
| 公開碼於抽籤時扣使用上限 | 匿名端點可被重複呼叫（無痕視窗即可），一人即可耗盡名額，使後續真實訪客看到「額滿」；事後雖可從紀錄識別，傷害已即時發生 → 抽籤不限次數、名額於 LINE 登記時認定 |
| 獎池各項目「本期剩餘名額」於抽籤時遞減 | 用於公開碼會重現上一列之耗盡問題；用於一次性碼則名額歸零時付費客人可能抽不到，違反「付費客人必中」→ 以人工「暫停」調整量能；待數據顯示量能集中再評估（例：僅對已登記之紀錄計數） |
| 公開碼採身分綁定或個別 claim token（防重抽挑項目） | 超出 MVP 範圍；重抽比例過高時再評估 |

**後台與資料**

| 方案 | 不採用理由 |
| :--- | :--- |
| 以 VPS Node 服務＋資料庫實作 | 違反 AI 功能「不保存使用者內容」之架構原則、增加維運；試算表讓兼職團隊可直接管理 |
| 演算法簽章碼（不需登錄即可驗證真偽） | 適用於大量發碼；本案發碼量小且每碼須記錄來源與已購項目 → 採**白名單制**：只有已登錄於「抽獎碼」工作表且狀態為啟用之碼有效 |
| 私訊碼、公開碼各一張工作表 | 欄位與邏輯重複，新增來源須再開表 → 改以「類型」欄位區分 |
| 人工於試算表手打抽獎碼 | 非程式背景之團隊易打錯、重複或打成規律字串 → 由程式產生 |
| 試算表自訂選單（按鈕發碼） | Google 試算表手機 App 不支援自訂選單與對話框，小編多以手機作業 |
| 試算表 `onEdit`（填一列、程式補齊） | 小編須有試算表編輯權，防呆僅靠下拉選單與保護範圍 → 改用表單 |
| 自製 Apps Script 後台 Web App | 開發量較大；以擁有者身分執行時，一般 Gmail 帳號通常無法取得使用者 email，須另設管理密碼 → 表單之已驗證 email 較簡單 |
| 小編直接編輯試算表之處理狀態（不設表單 C） | 登記受理時間可被覆寫、無法稽核 → 小編僅檢視，登記一律經表單 C |

**登記與稽核**

| 方案 | 不採用理由 |
| :--- | :--- |
| 表單 C 增加「LINE 原始訊息時間」欄位，以其排序名額 | 須小編人工抄寫、易出錯 → 以登記受理順序認定 |
| 處理狀態設四種（含 `已預約`），或只留 `已預約`／`已體驗` | 四種增加小編填寫次數；若無 `已登記`，小編可能於排定時間後才首次填寫，使受理時間延後、名額排序失準——第一個狀態必須代表「受理」 |
| 表單 C 嚴格單向狀態轉移（禁止跳級、倒退） | 小編填錯無法自行修正；稽核所需之登記受理時間已不可覆寫，中間狀態非名額認定所需 |
| 表單 C 另設「更正」流程（處理首次誤填） | 誤填為少見情形，增加表單複雜度 → 由管理者例外修正 |
| 抽獎紀錄受理欄位設保護範圍（僅擁有者可編輯） | MVP 僅少數管理者有編輯權、例外修正罕見，且編輯記錄可查回原值 → 列為人工控管；實際發生誤改再設定 |
| 「修正紀錄」工作表（原／新狀態、修改者、時間、原因） | 每次修正須多填一列；試算表內建編輯記錄已涵蓋修改者、時間、原值與新值 |

**技術細節**

| 方案 | 不採用理由 |
| :--- | :--- |
| 抽獎碼置於 query（`?code=`） | 會進入 nginx access log 與 GA4 之 `page_location` → 改用 fragment |
| 僅由 `/gacha` 頁面腳本 `replaceState` 清除碼 | 頁面腳本執行晚於 `<head>` 之 GA 設定，無法保證碼不進 GA4 → 於 `Layout.astro` GA 載入前處理 |
| 修改 `GoogleAnalytics.astro` 以送出去除 query／fragment 之 `page_location` | 會改變全站之 page_view 行為；僅於 `/gacha` 輸出之 inline script 影響範圍更小 |
| 節流計數改存試算表（持久化） | 每個請求（含被拒絕者）多一次試算表讀寫並須持鎖，反而加重鎖之負擔；節流定位為盡力而為，快取遺失之最壞結果為多出一批無效紀錄。許願池以同一模式於線上運作 |

- 備註：官網回訪價值之根本在於內容。「每日內容」（例：延伸占星抽卡之「今日星靈訊息」）為另一題目，不併入本 MVP。

## 十、 待決事項

### 1. 待業主決定（先以暫定值實作；正式對外開放活動前確認）

1. 資格門檻：哪些消費可獲得一次性碼（建議以單次消費金額為準，例：600 元以上；塔羅收費結構與其他服務不同，無 60 分鐘方案）；離線文字占卜（一題 300 元）是否計入。
2. 體驗時長（暫定 15 分鐘）與有效期限。
3. 加價購折抵金額與期限。
4. 公開碼之保底選項、各次活動名額，以及「不保證提供服務」「依登記受理順序」之對外用語。
5. 頁面、結果頁、社群貼文文案。
6. 「抽獎紀錄」處理狀態之分類（開發者建議 `已登記`／`已體驗`／`已轉換` 三種）。
7. 獎池是否維持九項（2026-11-13 新增三項為開發者代為決定），以及靈擺調頻「抽中即等同完整服務」是否需另行處理。
8. 老師激勵預算（日後）。

### 2. 待開發者決定

1. `PUBLIC_GACHA_API_URL` 未設定時之行為：顯示「暫未開放」，或比照許願池提供本機 Demo 模式（Demo 模式須明確標示，避免被誤認為正式結果）。
2. 抽籤儀式動畫形式。
3. Apps Script 回應格式與錯誤代碼。
4. 抽獎編號之長度與是否加前綴。
5. 節流數值（短視窗、每小時上限、`tryLock` 等待時間）之最終值。

### 3. 實作時須實測

1. 表單「收集已驗證之電子郵件」於一般 Gmail 帳號下之行為，以及 `onFormSubmit` 能否穩定取得填寫者 email。
2. 多張表單連結同一試算表時，觸發器依回應工作表區分來源表單之做法。
3. 寄信抵達時間（手機 Gmail 通知）是否足以支應 LINE 即時回覆客人。
4. 以 GA4 DebugView／即時報表確認 `/gacha#code=…` 進站時，page_view 之 `page_location` 不含抽獎碼；並確認 LINE 內建瀏覽器、Safari、Chrome 下 inline script 均能於 GA 前完成擷取。
5. 節流與鎖策略：以併發腳本測試公開碼（應回 `RATE_LIMITED`／`BUSY`，寫入筆數受上限約束），並確認測試期間一次性碼兌換與表單觸發器仍可正常完成。
